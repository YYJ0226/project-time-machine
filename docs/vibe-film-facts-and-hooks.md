## 已确认约束与论点

唯一案例为 Project Time Machine，自案例不等于自证正确。五至七分钟、16:9、无口播；顺序为动机／需求 → 技术路线 → 实验展示 → 边界与结论。旧十五秒卡片版只是对照原型。

一句话论点：最终软件展示“能做什么”；把需求、修改和检查的来路接起来，才能解释“它怎样被做出来”。核验仍需回到原始记录。

## 概念与具体形象

贯穿形象候选：一本摊开的“项目过程册”。每页有具体原文、PR 引用或检查项，不是只有标题的通用悬浮卡片。纸页动画标“证据组织示意”，不冒充产品真实录屏；真实界面另采。

## 三个开场方向

### A：找一条改动的来路（推荐）

先看到实际软件页面，再翻到背后的需求页。镜头从 Issue #3 的编号推到 PR #4 的 `Closes #3`；编号对上，却先停在“建议”。之后出现片名候选《开发的来路》，再引出平台。

主体是有具体内容的软件页面与原始资料，动作是翻页、找到同一编号、核对来源。前约三十秒只讲“一次改动怎样找到原需求”，不塞进全部架构、AI 和分享。优点是先让外行看懂一次操作，再解释平台价值。

### B：少了一页，能下结论吗？

过程册里有需求和修改，验证页暂时空着。停住提问，再出现“没采集到，不等于没做过”。缺页只能是明确标注的对照示意，不能暗示本项目确实缺测试。悬念强，但容易被误解成查漏或评分工具。

### C：在一次修改前按下暂停

沿真实事件页签翻动，到一条需求停下，再打开其实现与来源；结尾回到同一页。呼应“时光机”，但需要更早解释回放并非恢复旧代码环境。
